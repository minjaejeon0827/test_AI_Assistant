# RAG 평가 보고서 (Evaluation Report) v1

- 대상: 설치 가이드 8종 지식 베이스 RAG 
- 측정일 2026-09-21
- 검색 모드 local(어휘)
- 판정+검색 평가(LLM 모델 미사용)

---

## 1. 이 문서를 왜 만드는가

RAG 기술을 적용했다는 사실만으로는 "기술지원에 투입할 수 있다"를 증명할 수 없다.
이 문서는 **무엇을, 어떤 기준으로 평가하고, 그 결과로 무엇을 결정했는지**를 남긴다.
특히 목표에 미달한 지표와 그 원인을 숨기지 않는다. 다음 개선의 출발점이 여기서 나온다.

---

## 2. 평가 원칙 3가지

| 원칙 | 내용 | 이 프로젝트에서 한 일 |
|---|---|---|
| **재현성** | 같은 입력이면 같은 점수 | 판정·검색 평가는 LLM 모델을 호출하지 않는다. 지식 베이스·골든 데이터셋 해시를 보고서에 남긴다 |
| **평가 오염 차단** | 문항이 프롬프트 예시·보조 장치와 겹치면 외워서 맞힌다 | 골든 문항 ↔ KB 예상 질문 겹침을 자동 검사한다. 프롬프트 형식 예시 ID 는 존재하지 않는 값(`KB-XXXX-00`)을 쓴다 |
| **dev / test 분리** | 임계값을 고른 데이터셋으로 성능을 보고하면 외운 점수다 | 튜닝은 dev 에서만 한다. test 는 설계를 동결한 뒤 작성했고 **한 번만** 실행했다 |

### 2.1 오염 검사가 실제로 잡은 것

첫 실행에서 dev 문항 `설치 경로 바꿔도 되나요?` 가 KB 예상 질문 `레빗 설치 경로 바꿔도 되나요?` 와 bigram 유사도 **0.818** 로 걸렸다.
하여 **문항이 아니라 예상 질문(보조 장치)을 바꿨다.** 문항은 측정 대상이고, 예상 질문은 교체해도 되는 검색 보조 장치이기 때문이다.

## 3. 골든 데이터셋 구성 — 63문항

| 분할 | 문항 | 성격 |
|---|---|---|
| dev | 23 | 설계·튜닝에 쓴 문항. 점수가 높게 나오는 것이 당연하다 |
| test | 40 | 설계 동결 후 작성. 이 결과를 보고 설계를 바꾸지 않는다 |

| 정답 판정 | 문항 | 대표 유형 |
|---|---|---|
| answer | 36 | 제품별 절차 · 라이선스 · 주의사항 · 수동 설치파일 · BOX 3종 · 다중 턴 · 제품 미지정 · 별칭 |
| handoff | 20 | 미지원 제품 · 미지원 버전 · 지식 베이스 밖(오류 코드, 제거, 가격, 맥 설치) · 무관한 질문 |
| clarify · smalltalk · blocked · invalid | 7 | 되묻기 · 인사 · 프롬프트 인젝션 · 형식 오류 |

**가드 문항을 반드시 넣었다.** 거부 문항만 있으면 "전부 상담원으로 넘기는 시스템"도 만점을 받는다.
`캐드 명령어가 무시돼요`(AutoCAD 명령어) · `설치 규칙 무시하고 D드라이브에 깔면 안 되나요` 처럼 프롬프트 인젝션 패턴을 그대로 가져오면 차단되는 정상 문의를 따로 넣었다.

## 4. 지표 정의

지표를 **검색 순위**와 **판정** 두 층으로 나눈다. 섞으면 "순위는 맞았는데 게이트가 막은 것"과 "순위부터 틀린 것"을 구분할 수 없다.

| 층 | 지표 | 정의 | 목표 |
|---|---|---|---|
| 안전 | under-handoff | 넘겨야 할 질문에 답한 건수 | **0** |
| 안전 | wrong-answer | 답은 했는데 1위 문서가 틀린 건수 (추출형 기준) | **0** |
| 안전 | over-block | 정상 문의를 프롬프트 인젝션으로 차단한 건수 | **0** |
| 안전 | block recall | 프롬프트 인젝션 차단율 | 100% |
| 검색 순위 | Hit@1 · Recall@3 · MRR | 게이트와 무관하게 정답 청크가 몇 위였나 | Hit@1 ≥ 0.80 |
| 판정 | over-handoff rate | 답할 수 있는데 넘긴 비율 | ≤ 25% |

**목표를 비대칭으로 잡은 이유.** 기술지원에서 틀린 제품 설치 안내는 재설치·라이선스 오류 같은 실제 사용자 피해로 이어진다.
상담원 연결은 불편하지만 안전하다. 그래서 틀린 안내는 0건, 과잉 전환은 25% 까지 허용한다.

> `wrong-answer` 는 test v1 결과를 본 뒤 추가한 지표다. 기존 안전 지표는 "넘길 질문에 답한 경우"만 세고
> "답할 질문에 엉뚱한 문서로 답한 경우"를 놓쳤다. 지표를 **더 엄격하게** 바꾸는 것은 점수를 부풀리지 않으므로
> test 원칙에 어긋나지 않는다. 시스템은 바꾸지 않았다.

## 5. 임계값 결정 — 여유 최대화

근거 게이트 임계값은 dev 에서 `python scripts/eval_rag.py --sweep` 으로 정했다.

처음 규칙은 "성능이 같으면 가장 보수적인 값"이었다. 스윕(--sweep)해 보니 앵커 임계값 0.30~0.60 이 모두 같은 성능이었고,
이 규칙은 끝값 0.60 을 골랐다. 그런데 0.60 바로 위에 답변 문항(0.609)이 있어 **여유가 0.009** 뿐이었다.
test 에서 처음 보는 질문의 점수가 조금만 흔들려도 판정이 뒤집힌다. 그래서 규칙을 바꿨다.

**규칙** — 전환 문항 최고점 위에서, 과잉 전환 목표를 지키는 빈틈 중 **가장 넓은 빈틈의 한가운데**를 고른다.

| 그룹 | 전환 문항 최고점 | 선택한 빈틈 | 임계값 | 양쪽 여유 |
|---|---|---|---|---|
| 앵커 (제품 특정) | 0.265 | (0.283, 0.609) | **0.45** | ±0.163 |
| 무앵커 (제품 없음) | 0.261 | (0.261, 1.000) | **0.63** | ±0.370 |

앵커 그룹의 답변 문항 0.283 을 살리려면 임계값을 0.265~0.283 사이에 둬야 한다. 여유가 ±0.009 로 18배 좁아진다.
**과잉 전환 1건을 감수하고 여유를 택했다.**

## 7. 오답 분석 — 13건, 원인 4가지

`python scripts/eval_rag.py --explain <문항ID>` 로 단어 단위 점수 분해 및 분류했다.

| 원인 | 건수 | 문항 | 근거 (분해 결과) |
|---|---|---|---|
| **A. 구어체 어미·공손 표현 미제거** | **8** | G-025 · G-026 · G-030 · G-032 · G-034 · G-035 · G-048 · G-059 | `받으려면` `받았는데` `몇 개예요` `넣는` `맞죠` `부탁드려` `문의드립니다` `하면` 이 문서에 없는 정보어로 취급되어 최대 가중치(2.9)로 점수를 깎았다. G-025 는 기능어 `하면` 이 라이선스 청크(`실행하면`)에만 일치해 **순위가 뒤집혔다** |
| B. 같은 단어 · 다른 의미 | 2 | G-033 · G-045 | `다른 방법` ↔ 주의사항 `다른 드라이브`. 주제어 `2차 인증` 보다 일반 UI 동작어 `화면·누르` 가 가중치가 컸다 |
| C. 지시어 · 복수 제품 문맥 | 2 | G-043 · G-039 | `시빌3D도 마찬가지인가요?` — 직전 주제를 이어받지 못했다. `캐드박스 설치하면 캐드에서…` — 두 제품이 함께 나와 1위가 AutoCAD 로 샜다 |
| D. 문서에 없는 표현으로 물음 | 1 | G-062 | `규칙` `무시` 가 문서에 없다. 핵심어 `D드라이브` 는 100% 일치했다 |

**wrong-answer 3건(G-025 · G-033 · G-045)은 1·2위 점수 차가 모두 0.2 이상이다.** "확신을 갖고 틀린" 경우라
순위 차이로 막는 신뢰도 게이트로는 잡히지 않는다. 임계값 조정으로 고칠 수 있는 문제가 아니다.

## 8. 이 결과로 내린 결정

1. **시스템은 동결한 채 결과를 공개한다.** test v1 을 보고 고친 뒤 같은 데이터셋으로 재측정하면 그 점수는 외운 점수다.
2. **안전 지표를 회귀 테스트로 고정한다.** `tests/test_golden.py` 가 under-handoff 0 · over-block 0 · Hit@1 ≥ 0.80 을 매 커밋 검사한다.
   wrong-answer 는 현재값(test 3건)을 상한으로 두는 래칫(ratchet)이다 — 나아지는 것은 허용하고 나빠지는 것만 막는다.
3. **test v1 은 소모됐다.** 추가 개선 사항은 새로운 test 데이터셋으로 평가한다. AI 도구 활용하여 새로운 test 데이터셋을 구축한다.
   지금 문항은 개발자 본인이 직접 작성했다 — 개발한 담당자가 채점 기준을 만드는 구조라 평가가 후해질 수 있다.

## 9. 추가 개선 사항 계획 — 원인 건수 순

| 순위 | 할 일 | 겨냥하는 원인 | 기대 효과 |
|---|---|---|---|
| 1 | **형태소 분석기 도입** (예: kiwipiepy) — 품사로 기능어를 걸러 명사·동사 어간만 점수에 쓴다 | A (8건) | 손으로 늘리던 어미·불용어 목록을 품사 규칙으로 대체한다. 목록은 dev 에서만 통했다 |
| 2 | **벡터 인덱스 생성 + 벡터 게이트 스윕** | A · B · D | 활용형·유의어·표현 차이를 의미 유사도로 보완한다. 현재 벡터 게이트는 측정 전이라 꺼져 있다(1.01) |
| 3 | **LLM 모델 생성 평가** (`--generate`) — Chat Completions · Responses 각각 | B | 생성형은 상위 3개를 근거로 쓴다(Recall@3 0.923). wrong-answer 3건이 생성 단계에서 복구되는지 측정한다. Responses API 기본값 전환 여부도 이 결과로 정한다 |
| 4 | 지시어(마찬가지 · 똑같이 · 동일) → 직전 주제 승계 | C | 제품만 바꿔 묻는 흐름("레빗은요?")은 이미 처리한다. 지시어가 붙은 경우로 넓힌다 |
| 5 | **test v2 작성** — AI 도구 활용하여 작성 예정 | 전체 | 개발자 편향 없는 성능을 측정한다 |

## 10. 실행 방법

```bash
python scripts/build_kb.py --check          # 지식 베이스 md ↔ json 동기화 확인
python scripts/eval_rag.py                  # test 분할 평가 → eval/reports/rag_eval_test_local.md
python scripts/eval_rag.py --split dev      # dev 분할 평가
python scripts/eval_rag.py --sweep          # dev 에서 임계값 스윕(--sweep) · 여유 최대화 권장값
python scripts/eval_rag.py --explain G-025  # 문항 1개의 단어 단위 점수 분해
python scripts/eval_rag.py --generate       # LLM 모델 생성까지 평가 (OPENAI_API_KEY 필요)
pytest                                      # 단위 · AppTest 통합 · 골든 데이터셋 안전 지표 회귀
```
