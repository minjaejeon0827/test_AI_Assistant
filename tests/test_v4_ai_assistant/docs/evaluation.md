## 1. 이 문서를 왜 만드는가

RAG 기술을 적용했다는 사실만으로는 "기술지원에 투입할 수 있다"를 증명할 수 없다.
이 문서는 **무엇을, 어떤 기준으로 평가하고, 그 결과로 무엇을 결정했는지**를 남긴다.
특히 목표에 미달한 지표와 그 원인을 숨기지 않는다. 다음 개선의 출발점이 여기서 나온다.

## 2. 평가 원칙 3가지

| 원칙 | 내용 | 이 프로젝트에서 한 일 |
|---|---|---|
| **재현성** | 같은 입력이면 같은 점수 | 판정·검색 평가는 LLM 모델을 호출하지 않는다. 지식 베이스·골든 데이터셋 해시를 보고서에 남긴다 |
| **평가 오염 차단** | 문항이 프롬프트 예시·보조 장치와 겹치면 외워서 맞힌다 | 골든 문항 ↔ KB 예상 질문 겹침을 자동 검사한다. 프롬프트 형식 예시 ID 는 존재하지 않는 값(`KB-XXXX-00`)을 쓴다 |
| **dev / test 분리** | 임계값을 고른 데이터셋으로 성능을 보고하면 외운 점수다 | 튜닝은 dev 에서만 한다. test 는 설계를 동결한 뒤 작성했고 **한 번만** 실행했다 |

### 2.1 오염 검사가 실제로 잡은 것

첫 실행에서 dev 문항 `설치 경로 바꿔도 되나요?` 가 KB 예상 질문 `레빗 설치 경로 바꿔도 되나요?` 와 bigram 유사도 **0.818** 로 걸렸다.
하여 **문항이 아니라 예상 질문(보조 장치)을 바꿨다.** 문항은 측정 대상이고, 예상 질문은 교체해도 되는 검색 보조 장치이기 때문이다.

## 4. 지표 정의

지표를 **검색 순위**와 **판정** 두 층으로 나눈다. 섞으면 "순위는 맞았는데 게이트가 막은 것"과 "순위부터 틀린 것"을 구분할 수 없다.

| 층 | 지표 | 정의 | 목표 |
|---|---|---|---|
| 안전 | under-handoff | 넘겨야 할 질문에 답한 건수 | **0** |
| 안전 | wrong-answer | 답은 했는데 1위 문서가 틀린 건수 (추출형 기준) | **0** |
| 안전 | over-block | 정상 문의를 프롬프트 인젝션으로 차단한 건수 | **0** |
| 안전 | block recall | 프롬프트 인젝션 차단율 | 100% |
| 검색 순위 | Hit@1 · Recall@3 · MRR | 게이트와 무관하게 정답 청크가 몇 위였나 | Hit@1 ≥ 0.80 |
| 판정 | over-handoff rate | 답할 수 있는데 넘긴 비율 | ≤ 25% |

**목표를 비대칭으로 잡은 이유.** 기술지원에서 틀린 제품 설치 안내는 재설치·라이선스 오류 같은 실제 사용자 피해로 이어진다.
상담원 연결은 불편하지만 안전하다. 그래서 틀린 안내는 0건, 과잉 전환은 25% 까지 허용한다.

> `wrong-answer` 는 test v1 결과를 본 뒤 추가한 지표다. 기존 안전 지표는 "넘길 질문에 답한 경우"만 세고
> "답할 질문에 엉뚱한 문서로 답한 경우"를 놓쳤다. 지표를 **더 엄격하게** 바꾸는 것은 점수를 부풀리지 않으므로
> test 원칙에 어긋나지 않는다. 시스템은 바꾸지 않았다.

## 5. 임계값 결정 — 여유 최대화

근거 게이트 임계값은 dev 에서 `python scripts/eval_rag.py --sweep` 으로 정했다.

처음 규칙은 "성능이 같으면 가장 보수적인 값"이었다. 스윕(--sweep)해 보니 앵커 임계값 0.30~0.60 이 모두 같은 성능이었고,
이 규칙은 끝값 0.60 을 골랐다. 그런데 0.60 바로 위에 답변 문항(0.609)이 있어 **여유가 0.009** 뿐이었다.
test 에서 처음 보는 질문의 점수가 조금만 흔들려도 판정이 뒤집힌다. 그래서 규칙을 바꿨다.

**규칙** — 전환 문항 최고점 위에서, 과잉 전환 목표를 지키는 빈틈 중 **가장 넓은 빈틈의 한가운데**를 고른다.

| 그룹 | 전환 문항 최고점 | 선택한 빈틈 | 임계값 | 양쪽 여유 |
|---|---|---|---|---|
| 앵커 (제품 특정) | 0.265 | (0.283, 0.609) | **0.45** | ±0.163 |
| 무앵커 (제품 없음) | 0.261 | (0.261, 1.000) | **0.63** | ±0.370 |

앵커 그룹의 답변 문항 0.283 을 살리려면 임계값을 0.265~0.283 사이에 둬야 한다. 여유가 ±0.009 로 18배 좁아진다.
**과잉 전환 1건을 감수하고 여유를 택했다.**

## 8. 이 결과로 내린 결정

1. **시스템은 동결한 채 결과를 공개한다.** test v1 을 보고 고친 뒤 같은 데이터셋으로 재측정하면 그 점수는 외운 점수다.
2. **안전 지표를 회귀 테스트로 고정한다.** `tests/test_golden.py` 가 under-handoff 0 · over-block 0 · Hit@1 ≥ 0.80 을 매 커밋 검사한다.
   wrong-answer 는 현재값(test 3건)을 상한으로 두는 래칫(ratchet)이다 — 나아지는 것은 허용하고 나빠지는 것만 막는다.
3. **test v1 은 소모됐다.** 추가 개선 사항은 새로운 test 데이터셋으로 평가한다. AI 도구 활용하여 새로운 test 데이터셋을 구축한다.
   지금 문항은 개발자 본인이 직접 작성했다 — 개발한 담당자가 채점 기준을 만드는 구조라 평가가 후해질 수 있다.

- 함정 문항을 넣었다 — 문서 단어와 겹치지만 답하면 안 되는 질문: `나비스웍스 네트워크 라이선스 서버 설정`, `에너지박스 고객번호를 잊어버렸어요`, `윈도우 11 정품 인증 방법`.

### 12.3 봉인 절차 ([`eval/SEAL_test2.md`](../eval/SEAL_test2.md))

| 순서 | 한 일 |
|---|---|
| 1 | 개선 전 시스템 스냅샷 보관 |
| 2 | 문항 작성 → KB 예상 질문 · test v1 과 겹침 검사 → 1건(0.643) 봉인 전에 재작성 |
| 3 | sha256 `95b4145b957ca33d…` 기록 · 이후 시스템을 돌리지 않음 |
| 4 | 튜닝은 tune(dev + 퇴역 test v1, 63문항)으로만 |
| 5 | 개선 전 · 후 시스템을 test2 로 **각 1회** 측정 |

`eval_rag.py --split test2` 실행은 `eval/reports/test2_runs.log` 에 자동 기록된다. 기록은 3건이다.
1건은 비용 추정을 위해 **LLM 호출 대상 건수(33건)만** 집계한 것이고(지표 미출력), 나머지 2건이 개선 전 · 후 측정이다.

### 12.4 한계 — 완전한 독립 평가가 아니다

문항을 쓴 AI가 시스템을 설계한 모델과 같다. 같은 모델은 비슷한 표현을 떠올리기 쉽다.
코드 변경 전에 쓰고, 청크·문체를 체계적으로 배치해 영향을 줄였지만 없애지는 못했다.
**사람 검수(무작위 20문항 이상)를 거쳐 `reviewed_by` 를 채우기 전까지 이 점수는 참고치다.**

## 13. 개선 내용

### 13.1 형태소 분석기 (kiwipiepy) — 원인 A 대응

bigram 방식은 어미 · 기능어를 손으로 만든 목록으로 걸렀다. 목록은 dev 에서만 통했다(1라운드 dev→test 과잉 전환 20.0% → 34.6%).
형태소 분석기는 **품사로** 거른다.

| 질문 | bigram 단위 | 형태소 단위 |
|---|---|---|
| 인프라웍스 받으려면 어떻게 해야 돼요 | `받으`(문서에 없음 · 최대 가중치) | `받` |
| 레빗 2023 버전 수동 설치파일은 몇 개예요? | … `개예`(문서에 없음) | `버전` `수동` `설치` `파일` |
| c3d 수동설치 파일 부탁드려요 | … `부탁드려`(문서에 없음) | `수동` `설치` `파일` |

남기는 품사: 명사(NNG · NNP · NR) · 용언 어간(VV · VA) · 일반 부사(MAG) · 어근(XR) · 외국어 · 숫자.
품사로 걸러지지 않는 경동사(`하 · 되 · 드리`) · 질문 메타 명사(`방법 · 문의 · 법`) · 담화 부사(`좀 · 혹시`)는 **어간 하나씩만** 목록으로 둔다.

도입하면서 겪은 문제와 처리:

| 문제 | 원인 | 처리 |
|---|---|---|
| `켜야` → `늘` | bigram 시절의 원문 치환(`켜→실행`)이 문장을 망가뜨렸다 | 활용형 치환은 bigram 모드에서만. 형태소 모드는 어간 단위 동의어 |
| `레빗은요` → `은`(명사) | 제품명을 지운 자리에 조사만 남았다 | 지운 자리에 자리표시자를 넣어 조사로 붙게 함 |
| `manage` ↔ `manager` 동점 | 영문 부분 일치 | 영문 · 숫자 토큰은 완전 일치만 |
| `깔다가` → `깔다/NNG 가/JKS` | 분석기 오분석 | 동의어 사전에 `깔다 → 설치` 한 줄 |

kiwipiepy 가 없으면 자동으로 bigram 으로 내려간다. 두 방식은 점수 분포가 달라 **임계값을 따로 둔다.**

### 13.2 지시어 · 버전 전환 주제 승계 — 원인 C 대응

질문에 주제어가 없고 **제품 전환 · 버전 전환 · 지시어** 중 하나면 직전 질문의 주제를 이어받는다.

| 대화 | 결과 |
|---|---|
| 오토캐드 설치 위치 바꿔도 되나요? → **시빌3D도 마찬가지인가요?** | Civil3D 설치 진행 (주의사항) |
| 레빗 2026 라이선스 인증 방법 → **2025는요?** | Revit 라이선스 활성화 |
| 레빗 2026 라이선스 인증 방법 → **2023은요?** | 상담원 연결 — "라이선스 활성화 안내는 2025·2026 버전 기준" |

주제어가 하나라도 있으면 이어받지 않는다(새 질문으로 본다). 이어받으면 화면과 프롬프트에 그 사실을 알린다.

### 13.3 부가 제품 주체 판정 — 원인 C 대응

`캐드박스 설치하면 캐드에서 바로 쓰나요?` 처럼 BOX 제품과 그 호스트 제품이 함께 나오면 BOX 제품이 주어다.
관계는 코드가 아니라 지식 베이스에 선언한다(`## ADDON | CADBOX | AutoCAD`). 제품이 늘어도 코드를 고치지 않는다.

## 14. 임계값 재선정

형태소 모드는 점수 분포가 달라 tune 분할(63문항)에서 1라운드와 같은 **여유 최대화 규칙**으로 다시 골랐다.

| 그룹 | 넘길 문항 최고점 | 답할 문항 최저점 | 임계값 | 여유 |
|---|---|---|---|---|
| 앵커 | 0.216 | 0.588 | **0.40** | ±0.19 |
| 무앵커 | 0.382 | 1.000 (0.36 은 넘길 문항보다 낮아 포기) | **0.69** | ±0.31 |

무앵커 그룹은 답할 문항이 3개뿐이라 과잉 전환 목표(≤25%)를 지키는 빈틈이 없었다. 이때는 **안전을 우선**해 넘길 문항 최고점 바로 위를 고르도록 규칙에 명시했다.

> 규칙 결함 하나를 단위 테스트가 잡았다. 목표 제약이 없을 때 '가장 넓은 빈틈'을 고르면 답할 문항들 **위쪽** 빈틈이 뽑혀
> 아무 문항도 통과하지 못한다(벡터 게이트 시뮬레이션: 넘길 0.52 · 답할 0.64/0.71 에서 0.85 선택).
> 제약이 없는 경우는 "넘길 문항 최고점 ↔ 그 위 답할 문항 최저점"의 한가운데로 바꿨다.

## 16. test2 에서 발견한 결함과 핫픽스

| 문항 | 증상 | 원인 | 분류 |
|---|---|---|---|
| T2-050 `에너지박스 고객번호를 잊어버렸어요` | **인증 절차를 안내했다** (넘길 질문에 답함) | `고객 · 번호` 가 문서와 완전 일치(0.525). 어휘 점수는 "무엇에 관한 질문인가"는 보지만 **"절차를 묻는가, 문제 상황을 묻는가"는 구분하지 못한다** | 설계 빈틈 |
| T2-014 `Infraworks 라이센스 활성화는 어떻게…` | 상담원으로 넘김 | 원문 치환 `활성화→인증` 이 `활성화는`을 `인증는`으로 만들어 분석기가 `늘` 을 만들었다 | 구현 버그 (13.1 의 같은 계열을 다 잡지 못함) |

**결정** — test2 수치(넘길 질문 오답 1건 포함)는 **고치지 않고 그대로 보고한다.** 다만 안전 결함을 알고 두는 것은 서비스로서 옳지 않으므로 고쳤다.

| 핫픽스 | 내용 |
|---|---|
| 문제 상황 게이트 | 질문에 문제 상황 어휘(분실 · 오류 · 삭제 · 멈춤 등)가 있고 **지식 베이스가 그 어휘를 전혀 다루지 않으면** 상담원으로 넘긴다. 나중에 오류 대응 문서가 추가되면 게이트는 자동으로 풀린다 |
| 받침 기반 원문 치환 | 형태소 모드에서는 받침 유무가 같은 동의어 쌍만 원문에서 바꾸고, 나머지는 어간 단위로 바꾼다 |

**핫픽스 효과는 test2 점수로 주장하지 않는다.** 확인은 두 가지로만 했다.

- tune 분할 지표가 그대로다(무회귀) · bigram 폴백도 그대로다.
- T2-050 · T2-014 와 같은 유형을 회귀 테스트로 고정했다(`tests/test_pipeline.py`).

임계값은 동결했다. 핫픽스 후 스윕은 0.36 / 0.35 를 권하지만, 무앵커 권장값의 여유가 ±0.01 에 불과하다 —
**답할 문항이 3개뿐인 그룹에서 여유 최대화 규칙이 불안정하다**는 규칙의 약점이 드러났다. 다음 라운드에서 최소 여유 조건을 추가한다.
